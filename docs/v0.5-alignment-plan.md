# Gateway v0.5.0 Alignment Plan

Plan for updating the manager frontend from the agent-gateway **v0.4.3** Admin API
surface to the **v0.5.0** unified agent runtime surface.

Backend reference: `~/github/agent-guide/agent-gateway`, branch
`feature/unified-agent-runtime` (M0–M7 complete; M8/M9/M10 explicitly out of scope
for v0.5.0).

Backend design sources:

- `docs/plans/unified-agent-runtime.md` — §6.5 northbound contract, §6.7 admin API,
  §6.8 bundle model, §6.10 observability cutover, §9 breaking cutover
- `docs/design/builtin-agent-runtime.md`
- `docs/design/gateway-bundle-yaml.md` — §16 compatibility, §17 limitations
- `docs/design/virtual-key-rate-limiting.md`

## 1. Scope And Ground Rules

### 1.1 This is a hard cutover, not a migration

Plan §9 states: *"No runtime aliases, dual Admin endpoints, dual bundle fields, or
legacy route kinds are retained."* A v0.4.x store fails startup with
`legacy_agent_runtime_config`. There is therefore **no compatibility window**: the
manager targets v0.5.0 only, and no dual-path code is written.

### 1.2 The manager keeps writing through the Admin API

`gateway-bundle-yaml.md` §16 keeps every Admin API CRUD endpoint. Bundle YAML
changes the *recommended CLI write path*, not the API contract. The manager
continues to use `POST/PUT /admin/agents` and `/admin/agents/routes` directly.

The manager must **not** internally delegate writes to `agwctl gateway apply`:

- bundle apply is a single whole-file create-or-update, which collapses the
  manager's per-object RBAC actions (`gateway:write` vs `gateway:secrets_raw`)
  into one undifferentiated operation and degrades `audit_log` to a single row
- bundle apply has no prune, no diff, no plan (`gateway-bundle-yaml.md` §17), so
  its effect is not predictable enough to expose to a multi-tenant console

### 1.3 The manager is now the only interactive agent authoring surface

`cmd/agwctl/cmd_gateway_agent.go` exposes only `list / get / delete / workspace /
activity / usage / interactions / resources / health / cancel / decide / sessions /
transcript`. There is no `agent create` or `agent update` in the CLI — the only CLI
write path is `gateway apply -f`. This raises, not lowers, the importance of the
manager's agent form.

### 1.4 Bundle YAML and the Admin API share one model

`pkg/gatewaybundle/bundle.go` declares `Agents []agentpkg.Agent` and
`AgentRoutes []agentroute.AgentRouteConfig` — the runtime types themselves. The
loader is `YAML → generic → env expansion → JSON → typed structs`
(`gateway-bundle-yaml.md` §9), reusing the same `json` tags.

**A bundle `agents:` entry and a `POST /admin/agents` body are byte-identical.**
Unification already exists at the model layer; the frontend does not need to
unify the *input method* as well. This is what makes form ⇄ YAML switching a pure
serialization concern with no mapping cost.

## 2. Breaking Change Matrix

Derived from a route-table diff of `pkg/admin/routes.go` between `v0.4.3` and
`HEAD` (113 routes → 114 routes).

### 2.1 `/admin/acp/services` family removed (7 endpoints)

ACP execution config is inlined into the agent. `Agent.runtime.acp`
(`pkg/agent/types.go:62`) now holds `agent_type / cwd / allowed_roots /
default_model / env / config_overrides / idle_ttl / max_instances /
permission_mode / codex`. **`service_id` no longer exists.**

| v0.4.3 | v0.5.0 |
|---|---|
| `GET/POST /admin/acp/services` | *(removed — agent owns the config)* |
| `GET/PUT/DELETE /admin/acp/services/{id}` | *(removed)* |
| `GET /admin/acp/services/{id}/sessions` | `GET /admin/agents/{id}/sessions` |
| `GET /admin/acp/services/{id}/sessions/{sid}/transcript` | `GET /admin/agents/{id}/sessions/{sid}/transcript` |

### 2.2 `/admin/acp/routes` → `/admin/agents/routes`

New model `kind=agent, protocol=agent`, target field `agent_id` instead of
`service_id` (`pkg/gateway/agentroute/types.go`). Generated ID becomes
`agent:<agent_id>:<path_prefix>`.

`Agent.routes` drops `acp_route_ids`; only `llm_route_ids` and `mcp_route_ids`
remain. An agent's ingress routes are discovered by querying agent routes and
filtering on `agent_id`.

### 2.3 ACP runtime endpoints re-keyed from service to agent

| v0.4.3 | v0.5.0 |
|---|---|
| `POST /admin/acp/runtime/permissions/{request_id}` | `POST /admin/agents/{id}/permissions/{request_id}` |
| `DELETE /admin/acp/runtime/threads/{service_id}/{thread_id}` | `DELETE /admin/acp/runtime/agents/{agent_id}/threads/{thread_id}` |
| `GET /admin/acp/runtime` | unchanged path; response objects now carry `agent_id` (`pkg/admin/acp.go:39-56`) |

### 2.4 Data-plane turn body is now strict

The AgentRoute decoder uses `DisallowUnknownFields` and accepts only
`input / session_id / permission / options`
(`pkg/agent/runtimeapi/decode.go`). Unknown top-level fields return
`400 unsupported_option`; a missing `options.version` returns `400 invalid_request`.

The manager currently sends a flat body
(`app/api/admin/acp/chat/turn/route.ts:67-76`) and **will be rejected outright**.

```jsonc
// v0.4.3 (rejected by v0.5.0)
{ "thread_id": "...", "input": "...", "cwd": "...", "model": "...",
  "fresh_session": true, "config_overrides": {} }

// v0.5.0
{ "input": "...", "session_id": "...",
  "options": { "version": "v1",
    "runtime": { "thread_id": "...", "cwd": "...", "model": "...",
                 "fresh_session": true, "config_overrides": {} } } }
```

Field names are unchanged; they move under `options.runtime`
(`pkg/gateway/runtime_backends.go:22-26`).

### 2.5 Observability dimensions cut over

Agent data-plane traffic is now `route_kind=agent, route_protocol=agent` — the
route config normalizes both (`pkg/gateway/agentroute/types.go`), and the
dispatcher copies them into the usage span (`pkg/dispatcher/handler.go:192`).

The manager's Usage → ACP tab Source selector filters data-plane traffic on
`route_protocol=acp`, which **now matches nothing and returns silently empty**.
Admin audit spans still use `route_protocol=admin`
(`pkg/admin/acp.go:beginACPAdminAudit`). The `/admin/metrics/acp/*` endpoints
themselves are unchanged.

## 3. New Capabilities

### 3.1 `runtime.type = "builtin"`

In-process ADK agent, no external CLI process (`pkg/agent/builtin_types.go`):

- `model.llm_route_id` + `model.model` + `model.retry.max_retries` (1–5)
- `topology.kind`: `single | sequential | parallel | loop | supervisor |
  planexecute | deep | custom`, plus `factory`, `max_iterations`,
  **recursive inline `sub_agents`**, and `plan_execute` role overrides
- `tools[]`: `{ mcp_service_id, tools[] }`
- `middlewares`, `permissions` (`auto_approve | interactive`, `timeout_seconds`,
  `max_pending`, `auto_approve_tools` as `<service_id>/<tool_name>`), `limits`

### 3.2 Capability discovery

`GET /admin/agents/{id}/capabilities` returns the authoritative
`runtimeapi.Capabilities` (`pkg/agent/runtimeapi/types.go`):

```jsonc
{ "executable": true,
  "turn": { "streaming": true },
  "sessions": { "resume": true, "list": true, "transcript": true, "durable": false },
  "permissions": { "interactive": true, "resume_mode": "active_stream" },
  "cancellation": { "force": true, "graceful": true },
  "events": ["session", "delta", "..."] }
```

This becomes the **single source of truth** for which tabs and actions the UI
shows, replacing every hardcoded `runtime.type === "acp"` check.

### 3.3 Run lifecycle

- `GET /admin/agents/{id}/runs` → `{ items: RunInfo[], durable: false }`
- `DELETE /admin/agents/{id}/runs/{run_id}?mode=force|graceful` (default `force`;
  unsupported mode returns `501 capability_not_supported`)

### 3.4 Builtin host diagnostics

`GET /admin/builtin/runtime` and `GET /admin/builtin/runtime/inflight`.

### 3.5 Virtual key rate limiting

`VirtualKey.rate_limits.{llm,mcp,agent}.{requests_per_minute,burst}`
(`pkg/gateway/virtualkey/types.go`). Backend decoding is strict — unknown fields
are rejected.

### 3.6 Unified error contract

`{ error_type, message }` with stable codes: `agent_not_found`, `agent_disabled`,
`runtime_not_executable`, `capability_not_supported` (501), `unsupported_option`
(400), `invalid_request`, `backend_unavailable` (may carry `Retry-After`).

### 3.7 Additional SSE events

Beyond the existing ten: `available_commands`, `session_info`, `mode`,
`config_options`.

## 4. Design Decisions

### D1 — ACP agents keep a form; builtin agents get a YAML editor

`runtime.acp` is ~10 flat fields and already has working form UI (currently on the
ACP Services page). Moving it into the agent form's Runtime step is relocation,
not redesign. Downgrading a working, validated, dropdown-driven form to a
textarea for the sake of surface-level consistency is a net loss.

`runtime.builtin` has recursive `topology.sub_agents` plus middleware, permission,
limit, retry, and plan-execute role blocks. Full visual editing approaches the
cost of a second agent form, against a v0.5.0 goal of validating the backend.

**Decision:** ACP → form. Builtin → YAML/JSON editor with client-side schema
validation, submitted through `POST /admin/agents` unchanged. Users can paste
`agwctl gateway export` output directly. Incremental form coverage for builtin
topologies (`single`, `sequential` first) is deferred past v0.5.0.

### D2 — Unification is a bidirectional view, not a single input method

Because the models are isomorphic (§1.4):

1. Every agent detail page gets a **read-only YAML view** emitting a fragment that
   pastes straight into `agwctl gateway apply`
2. A global **Import / Export Bundle** page
3. **Form ⇄ YAML toggle** (advanced mode) — ACP form-first, builtin YAML-first

### D3 — Bundle import is decomposed client-side, with a dry run

Import parses YAML in the manager, then issues **per-object Admin API calls**,
preserving RBAC granularity and audit rows (§1.2). Before executing, it renders a
`create / update / skip / conflict` preview.

This also supplies the `diff` / `plan` capability the backend lacks
(`gateway-bundle-yaml.md` §17) — the manager's real increment over the CLI.

### D4 — Capabilities drive the UI

Tab visibility, button enablement, and degraded states derive from
`GET /admin/agents/{id}/capabilities`, never from `runtime.type`.

### D5 — Non-executable runtimes must be prominent

M8 is out of scope, so HTTP agents report `capabilities.executable=false` and
`POST /turn` returns `501 runtime_not_executable`. Plan §6.6 requires:
*"Admin/CLI views must show the non-executable state prominently so an
existing-but-inactive route is not misdiagnosed as a matcher or authentication
defect."*

This is a hard v0.5.0 UI requirement, not an ordinary badge: the agent list row,
detail header, and any agent route bound to a non-executable agent must all carry
an explicit warning state.

>     return
> }
> h.mux.ServeHTTP(rr, r)
> ```
>
> `routes` is therefore a hard-reserved agent ID (see §8.4). The manager's action
> map and any client-side path building must treat the literal segment `routes` at
> position 2 as the route collection, never as an agent id.

## 8. Backend Gaps To Report

Found while analysing; worth resolving before v0.5.0 ships.

1. **`docs/design/gateway-bundle-yaml.md` §8 is stale.** It lists the implemented
   scope as `providers / managedModels / routes / virtualKeys`, but
   `pkg/gatewaybundle/bundle.go:35-43` already carries `mcpServices`, `mcpRoutes`,
   `agents`, `agentRoutes`, and `cliAuthAuthenticators`.
2. **`credentials` are still absent from bundle apply/export** (§17). Any
   manager import/export inherits that hole and must say so in the UI.
3. **No `agent create` / `agent update` in agwctl.** Intentional per §16, but it
   means an operator with only the CLI cannot author an agent except through a
   full bundle file. Worth confirming this is the intended v0.5.0 story.
4. **An agent with `id: "routes"` is silently unreachable.**
   `pkg/admin/handler.go:187-191` dispatches on a literal path prefix before the
   main mux, so for such an agent `GET /admin/agents/routes` returns the *route
   list* instead of the agent, and `/admin/agents/routes/workspace` 404s in the
   routes mux. Nothing rejects the id at create time — `Agent.Validate()`
   (`pkg/agent/types.go`) only requires non-empty `id`/`name`. Recommend
   rejecting `routes` as a reserved agent ID in `Validate()`. The manager will
   guard client-side regardless, but the API should fail closed.
5. **No `/admin/metrics/builtin/*` family**, while §6.10 states
   `builtin_usage_events` remains a valid store. Builtin-specific metrics are
   currently only reachable through the generic interactions query — confirm
   whether that is intended for v0.5.0.
