# Manager v0.1.0 Release Plan

- Document type: **delivery**
- Status: **accepted tagged release baseline**
- Applies to: `main` and annotated tag `v0.1.0`
- Last reviewed: 2026-10-22

Gateway baseline: `agent-gateway` tag `v0.7.0`, Community commit
`3d04b7a0207a6d31746a1b196ae9d82097c2087c`

This release establishes the minimum manager compatibility baseline that
precedes the Agent resource platform rebuild. The rebuild documented in
[the Agent resource platform rebuild plan](../archive/agent-resource-platform-integration-plan.md)
currently descends from the final `v0.1.0` tag; this ancestry records the
one-time history repair and does not require later feature work to be replayed
at that tag. None of its resource-domain
schemas or APIs are part of this release. The old `v0.1.0` tag pointed to a much
earlier Gateway v0.4-era manager commit
`26a8a940d08a7d8838cc8d278e91c8551dce18f6` and was retired before this release
line reused the version.

## 1. Release outcomes

v0.1.0 delivers two independently verifiable outcomes:

1. The existing manager workflows target the published Agent Gateway v0.7.0
   HTTP contracts, including executable remote HTTP/A2A Agents.
2. The existing manager interface is available in English (`en-US`) and
   Simplified Chinese (`zh-CN`) without changing canonical application URLs.

The version was considered complete only after the implementation and acceptance
gates below passed on a clean tree and the annotated `v0.1.0` tag was created.

## 2. Agent Gateway v0.7.0 boundary

### 2.1 Required compatibility

- Replace the pre-execution HTTP Agent shape
  `runtime.http.{endpoint,auth_ref}` with the published shape
  `runtime.http.{card_url,protocol,auth_ref,timeout_seconds}`.
- Require `protocol: a2a`; reject the legacy `endpoint` field in form, YAML and
  Gateway Bundle validation.
- Allow both common `protocol: agent` and native `protocol: a2a` Agent routes in
  route management. The browser chat bridge accepts only a common `agent` route,
  because native A2A ingress does not expose the manager's `/turn` or
  `/permission` contract.
- Drive Chat, sessions, permission and cancellation affordances from Gateway
  capabilities. HTTP Agent cancellation keeps the v0.7.0 retryable
  `backend_unavailable` semantics.
- Preserve the data-plane connection URL when an Agent route uses a virtual
  Host, strip the inbound browser Host from Admin forwarding, propagate request
  cancellation, and do not impose a client body timeout on a valid streaming
  turn.
- Exercise Agent create, AgentRoute create, authenticated common-turn SSE and
  virtual-Host routing against a Gateway built from the exact published tag.

### 2.2 New v0.7.0 surfaces

v0.7.0 also adds runtime manifests, extension envelopes, contributed Admin
subroutes and selectable Virtual Key limiter backends. They are compatible with
the manager's authenticated proxy and Gateway Bundle boundary, but v0.1.0 does
not claim a dedicated extension-authoring UI or management of independently
compiled commercial modules. Absence of that optional UI does not block the
existing manager workflows or HTTP/A2A Agent compatibility defined above.

The manager must not weaken its existing authorization or secret redaction to
expose these surfaces. A later dedicated UI requires its own action mapping,
redaction review and negative authorization tests.

### 2.3 Source discipline

The old `feature/agent-resource-platform` commit
`ad9c636742f7f4ef6fd022c787258a7096a030a9` is implementation evidence for the
HTTP/A2A contract and transport behavior. Port it by contract; do not merge the
old branch or import its resource-platform documentation and schemas into this
release.

## 3. Internationalization boundary

### 3.1 Locale contract

- Supported locales are `en-US` and `zh-CN`.
- Existing paths such as `/dashboard/agents` remain canonical. Locale prefixes
  are not added to URLs, so bookmarks, direct authorization checks and Gateway
  scope paths remain stable.
- The selected locale is stored in a same-site cookie and is applied before the
  dashboard renders. The root document exposes the matching `lang` attribute.
- The language selector is keyboard accessible and available on login and in
  the authenticated shell.
- Unsupported or malformed locale values fall back to `en-US`.

### 3.2 Translation coverage

The release translates the existing user-facing manager surface:

- authentication, navigation, headers and account controls;
- page titles, descriptions, tabs, filters and empty/loading/forbidden states;
- forms, field help, client validation, confirmations and notifications;
- tables, charts, runtime controls and accessibility labels; and
- manager-owned error messages with stable translation keys.

Identifiers, enum values, protocol names, code/YAML, timestamps, Gateway
payloads and arbitrary upstream error text remain unchanged. Where the Gateway
returns a stable error code, the UI may translate the manager-owned explanation
while preserving the original diagnostic detail.

Developer documentation is not duplicated into two languages by this release.
The multilingual claim applies to the product UI and its manager-owned feedback.

### 3.3 Implementation rules

- Translation catalogs are typed and owned inside this repository.
- Components request semantic message keys; new code must not select behavior by
  comparing translated display strings.
- Interpolation and plural/count rendering escape values through React; catalogs
  never contain executable markup.
- Server and client rendering use the same initial locale to avoid hydration
  mismatches.
- Locale tests cover fallback, persistence, switching and representative
  navigation/form/error rendering in both languages.

## 4. Version and history sequence

The obsolete intermediate v0.2.0 preparation, the documentation reset and the
final v0.1.0 preparation were consolidated into one release-baseline commit.
The resulting history keeps the language-switcher correction independently
reviewable and contains no intermediate package-version transition:

```text
d786da7
  -> a79102b docs(release): define v0.2.0 gateway and locale baseline
  -> d3ee992 feat(gateway): align manager with Agent Gateway v0.7.0
  -> 6a08a77 feat(i18n): add locale runtime and language selection
  -> a874f0e/6132261/3447d89/81b699d translate the existing interface
  -> refactor(i18n): restyle language switcher
  -> docs(release): establish manager v0.1.0 baseline
  -> annotated tag v0.1.0
```

The existing `rebuild/agent-resource-platform` branch already contains the
Step 0–4 series from an earlier release candidate. Recovery refs were created
before rewriting the release history, and the ordered implementation series was
rebased once so that `v0.1.0` became its ancestor on 2026-10-20. Later steps are
normal feature-branch commits after that series; the release plan imposes no
permanent exact-base or replay requirement on the branch.

## 5. Acceptance gate

Before creating the tag:

- all Bun unit/integration tests pass;
- ESLint and TypeScript checks pass;
- the production build succeeds;
- `git diff --check` passes;
- existing authentication, multi-user, multi-Gateway, secret-redaction and
  Gateway-management behavior remains intact;
- representative English and Chinese direct-load, refresh and language-switch
  flows pass without hydration errors;
- the HTTP Agent smoke passes against the exact Gateway v0.7.0 commit in both
  development and production manager modes; and
- the release commit and tag are created from a clean worktree, with
  `package.json` reporting `0.1.0`.

## 6. Explicit exclusions

- Agent resource platform Steps 0–9;
- Tenant/resource schemas, resource APIs and deployment orchestration;
- workflow engines, schedules or workers;
- a commercial extension/module implementation;
- a dedicated extension-envelope administration UI; and
- locale-prefixed routing or translated developer documentation.

## 7. Final verification record

The final release candidate was verified on 2026-10-20 against Bun 1.3.13 and Agent
Gateway v0.7.0 commit
`3d04b7a0207a6d31746a1b196ae9d82097c2087c`:

- `bun test`: 83 passed, 0 failed;
- `bun run typecheck`: passed;
- `bun run lint`: passed;
- `bun run build`: passed;
- `git diff --check`: passed;
- `bun run smoke:http-agent`: passed in development and production manager
  modes against the pinned Gateway source archive; and
- production direct loads rendered matching `html[lang]` and login content for
  default `en-US` and the persisted `agwmngr.locale=zh-CN` cookie.

The locale unit tests additionally cover supported-locale fallback, translation
parity and the path-wide same-site language-switch cookie. This verification
includes the language-switcher correction, and `package.json` reports `0.1.0`.
